1 · File Overview

Purpose. bot.ts is the single boot-and-lifecycle harness every bot in the monorepo runs through. Each bots/*/src/index.ts does a top-level await createBot({...}) and supplies only intents, a commands directory, and an optional setup() hook. Everything else — environment validation, secret hydration, health server, database connections, command dispatch, authorization, rate limiting, audit logging and graceful shutdown — is owned here.

2 · Errors Identified

High F-01 — Startup-cancelled shutdown is a silent no-op bot.ts:725-726 ↔ 774 / 782

shutdown() opens with an idempotency guard on the same flag that the early signal trap sets:

// 364-369 — early trap, registered before any startup work
let shuttingDown = false;
const onStartupSignal = () => { shuttingDown = true; };
process.once('SIGTERM', onStartupSignal);
process.once('SIGINT',  onStartupSignal);

// 724-727 — teardown refuses to run if that flag is already set
const shutdown = async (signal) => {
  if (shuttingDown) return;      // ← fires on the cancelled-startup path
  shuttingDown = true;
// 773-784 — the catch that is supposed to drive teardown
try {
  assertStartupActive(shuttingDown);   // throws if a signal arrived during startup
  ...
} catch (err) {
  // "drive the normal teardown so the log buffers holding the
  //  failure diagnostics are flushed before the process exits"
  await shutdown('BOOTSTRAP_FAIL');    // ← immediately returns, does nothing
  throw err;
}
Impact
  • The documented teardown never runs on this path: server.close(), baseSink.stop(), backupSink.stop(), client.destroy() and both client.close() calls are all skipped.
  • Buffered audit logs are lost — precisely the diagnostics the comment claims to preserve.
  • The listening socket is abandoned until the process dies.
  • Reachable whenever SIGTERM/SIGINT lands in the window between line 369 and line 768 — which includes the ~27–54s Mongo connect phase, the longest part of startup.

High F-02 — Graceful shutdown during startup is reported as a crash bot.ts:779-784

The catch block unconditionally rethrows, with no distinction between "startup genuinely failed" and "a normal SIGTERM arrived":

} catch (err) {
  await shutdown('BOOTSTRAP_FAIL');
  throw err;   // ← always propagates, even after a clean teardown
}

All eight callers use bare top-level await createBot({...}) with no surrounding try/catch (e.g. bots/cyrene/src/index.ts:10, bots/luffy/src/index.ts:9). An ESM top-level rejection terminates Node with a non-zero exit code.

Impact
  • A clean, operator-initiated restart is indistinguishable from a crash: Render sees exit ≠ 0 and can mark the deploy/instance as failed.
  • Alerting and crash-rate dashboards are polluted by routine restarts.
  • Note the ordering subtlety: when the signal arrives after line 770 the real shutdown handler runs correctly and tears down fully — and the code still throws afterwards, discarding the clean result.

Medium F-04 — Mongo reconnect has no in-flight dedupe; assign can leak a client bot.ts:696-721

const reconnect = setInterval(() => {
  if (shuttingDown) return;
  if (!mongoHandle) launchReconnect(() => connectMongo(env, log), (h) => { mongoHandle = h; }, 'primary');
  ...
}, 60_000);

launchReconnect registers the promise in reconnecting but never records that an attempt is already in flight for that slot. If one attempt outlives the 60s tick, the next tick launches a second connect for the same handle. Both can resolve, and the second assign(handle) overwrites the first — the first MongoClient is never closed.

Impact
  • Connection-pool leak; the M0 free tier caps at 500 connections across everything (mongo.ts:167).
  • Worst-case connectMongo is ~27s (3 × 8s selection timeout + 1s + 2s backoff), so overlap needs a network stall — conditional, but real under exactly the conditions that trigger reconnects.

Medium F-07 — Index creation shares the connect retry, so an index failure discards a healthy connection db/mongo.ts:173-190

try {
  await client.connect();
  const collections = buildCollections(db);
  await ensureIndexes(collections);   // ← same try block as connect()
  return { client, db, collections };

...

ensureIndexes issues eight createIndex calls, three of them {unique:true}. If pre-existing data violates a unique constraint (duplicate (guild_id,user_id) rows in xp, card_games or inventories), the index build fails, the error is classified as a connection failure, and the bot runs with no database at all.

Impact
  • A data-integrity problem is reported and retried as an infrastructure problem — the retry can never succeed, so the bot stays degraded on every boot until someone fixes the data.
  • Also runs 8 index requests per bot × 8 bots ≈ 64 concurrent index operations against one M0 cluster at boot.

3 · Lost Points / Weak Areas

Test coverage gaps
  • bot-shutdown.test.ts exercises only the two exported helpers in isolation (withShutdownTimeout, assertStartupActive). It never drives createBot, so F-01 and F-02 are structurally invisible to the suite — the tests assert the guard works, not that teardown happens.
  • No test covers the button-interaction branch (590–623) at all, including the interaction.message.author access in F-03.
  • No test asserts buildDashboardEmbed bounds or the empty-embed case (F-08).
  • No test asserts the reconnect loop's concurrency behaviour (F-04).
Error-handling and observability
  • renderFailure (220–240) never logs — it relies entirely on guard upstream, so the terminal branch at 239 tells the user "reported automatically" with no local evidence.
  • Startup failures are asymmetric: vault hydration failures are swallowed and degraded (385–395), while database failures are silent (they return null). Only login() failures are loud.
  • No Events.Warn / Events.ShardError listener — gateway warnings are invisible.
  • installProcessGuards and initSentry are wired at 403–404, after the port binds and after hydration, so early-startup faults are never reported to Sentry.
Design / readability
  • createBot is a single 425-line function holding ~20 mutable bindings. The shutdown and reconnect closures over mongoHandle / shuttingDown are the direct source of F-01 and F-04; extracting a small lifecycle state object would make both impossible to write.
  • CreateBotOptions.setup (98) has a four-way union return type that is hard to read at the call site.
  • Two loggers coexist (bootstrapLog 375, log 401) with no clear handoff contract.
  • safeUrl (246-255) accepts http: for image/thumbnail, which Discord generally requires to be HTTPS.

4 · Root Cause Analysis

IDRoot causeWhy it matters
F-01 One boolean (shuttingDown) is doing two jobs: "a shutdown was requested" and "teardown has already run". The early signal trap sets the first; the idempotency guard reads it as the second. Conflating a request flag with a completion flag is the classic idempotency bug. Any signal during startup poisons the flag and permanently disables the very cleanup the catch block was written to perform.
F-02 Startup cancellation and startup failure funnel into one catch that always rethrows. Exit code is the only signal a supervisor has. Reporting a clean, requested shutdown as a crash corrupts deploy status and alerting, and trains operators to ignore failures.
F-03 The button branch was added above the existing try without being wrapped in its own. Discord's partial-message model means .author is legitimately nullable. Treating a documented nullable as always-present converts an edge case into an unhandled rejection.
F-04 The interval checks state (!mongoHandle) but never intent (is a connect already running?). Polling loops must dedupe on in-flight work, not just on the resulting state. Without it, slow operations overlap and the last writer wins, orphaning the earlier resource.
F-05 An authorization identifier was written as a literal instead of configuration. Privilege identifiers must be rotatable without a code deploy; duplicating them across three layers guarantees eventual drift.
F-06 Two independent awaits written in sequence rather than composed with Promise.all. Serialising independent I/O multiplies worst-case latency, and here it lands directly in the deploy-critical startup path.
F-07 Schema preparation was placed inside the transport retry boundary. Retrying a non-retryable error is worse than failing: it burns the retry budget, mislabels the fault class, and produces a permanently degraded service that looks like a network problem.
F-08 Validation was applied per-field (bounds on each value) but never at the object level (is the result non-empty?). Field-level bounds do not imply a valid composite. An all-optional builder needs one final "did we set anything?" assertion.
F-09 Code predates the discord.js 14.14+ flags migration. Deprecated-but-working APIs are cheap to fix now and expensive to fix during a forced upgrade.
F-10–F-22 Accumulated small oversights: unbounded caches, dead branches, inconsistent aggregation, global state, strict string compares. Individually minor; collectively they raise the cost of every future change and hide real faults in noise.

5 · Solutions & Recommendations

F-01 Split the request flag from the completion flag

Introduce a dedicated teardown guard so a cancelled startup still tears down, while double-shutdown stays impossible:

let shuttingDown = false;      // "a shutdown was requested" (set by the early trap)
let teardownStarted = false;   // "cleanup has run" (set only by shutdown)

const shutdown = async (signal: string): Promise<void> => {
  if (teardownStarted) return;   // idempotent on the right flag
  teardownStarted = true;
  shuttingDown = true;
  log.info({ signal }, 'shutting down');
  // ...unchanged body...
};

Add a regression test that actually drives the path rather than the helper:

it('runs teardown when startup was cancelled by a signal', async () => {
  // arrange a createBot whose mongo connect hangs, fire SIGTERM mid-startup,
  // then assert baseSink.stop() / server.close() were invoked and no throw escaped.
});

F-02 Distinguish cancellation from failure; exit 0 on a clean shutdown

try {
  assertStartupActive(shuttingDown);
  const cleanup = await options.setup?.({ client, services, log, env });
  setupCleanup = typeof cleanup === 'function' ? cleanup : undefined;
  assertStartupActive(shuttingDown);
  await client.login(env.discordToken);
} catch (err) {
  await shutdown('BOOTSTRAP_FAIL');
  // A requested shutdown is not a failure.
  if (shuttingDown && !(err instanceof Error && err.message === 'startup cancelled by shutdown')) {
    throw err;
  }
  return /* never reached: process is exiting */;
}

Cleaner still: give assertStartupActive a dedicated sentinel error class (StartupCancelledError) and branch on instanceof instead of a message comparison. Then call process.exit(0) after teardown on that branch so supervisors see a clean, intentional stop.

F-04 Dedupe on intent, and close any superseded handle

const inFlight = new Set<'primary' | 'secondary'>();

const launchReconnect = (slot, connect, assign, label) => {
  if (inFlight.has(slot)) return;          // already connecting
  inFlight.add(slot);
  const pending = connect()
    .then(async (handle) => {
      if (!handle) return;
      if (shuttingDown) { await handle.client.close().catch(() => undefined); return; }
      // never orphan a previously-assigned handle
      const previous = slot === 'primary' ? mongoHandle : secondaryMongoHandle;
      if (previous && previous !== handle) {
        await previous.client.close().catch(() => undefined);
      }
      assign(handle);
      log.info(`${label} mongodb reconnected`);
    })
    .catch((err) => log.error({ err }, `${label} mongodb reconnect failed`))
    .finally(() => inFlight.delete(slot));
  reconnecting.add(pending);
  void pending.finally(() => reconnecting.delete(pending));
};

Overall assessment

Solid, security-conscious engineering with a weak lifecycle layer. This is not a neglected file. The defensive choices are deliberate and mostly correct: strict option sanitisation, fail-closed authorization ordering, embed field bounds that match Discord's caps, a redaction pass over audit metadata, TLS enforcement for Mongo, batched log writes to protect a free-tier write cap, and a health endpoint that separates liveness from readiness — the fix that made Render deploys viable. Verified non-issues were checked rather than assumed (the servers table exists; the pre-setDependencies window is handled; connectMongo cannot throw; the redaction regex is stateless).

The weakness is concentrated in one place: createBot is a 425-line function whose shutdown and reconnect logic share mutable state across long-lived closures. Both High findings and F-04 are the same underlying mistake — a flag or a timer standing in for explicit lifecycle state. F-01 and F-02 are especially instructive because they are mutually reinforcing: the code that was written to guarantee cleanup is disarmed by the very signal it is meant to handle, and then reports the resulting exit as a crash.

The testing story explains why these survived. bot-shutdown.test.ts tests the helpers, not the behaviour — it proves assertStartupActive(true) throws, which is the mechanism causing the bug, not the outcome the comment promises. The suite is green and the defect is real, which is the signature of unit tests asserting implementation rather than behaviour.
